# Jot / Screen Tutor — Implement Course Knowledge and Student Mastery

## Mission

Extend the existing Jot / Screen Tutor application into a source-grounded learning system. Implement hierarchical course-material retrieval, a class-scoped concept graph, a secure question bank, four-stage Mastery Ladder assessments, XP and accuracy accounting, evidence-based student mastery, progress views, adaptive practice, and calibration telemetry. Deliver working backend behavior, database upgrades, frontend flows, and meaningful automated tests. This is an implementation request, not an architecture-only exercise.

Work through the dependency phases below without pausing for approval after each phase. Inspect the repository first, reuse its current services, and report any genuine blocker and the independent work completed around it. Never present planned or partially wired behavior as complete.

**Product decision for this task:** Persist assessment-derived, student-private XP, responses, mastery evidence, projections, and progress history. Update the product and role-specific design docs to reflect that decision. This does not authorize recording screen frames, microphone audio, raw Live transcripts, or tutoring conversations; existing explicitly opted-in recap behavior remains separate. It does not authorize teacher access to an individual student's progress, leaderboards, or instructor-facing class-wide performance analytics. Access-controlled aggregate telemetry for internal question and graph calibration is in scope.

## 1. Structured, revisioned material retrieval

Extend the existing upload processors for PDF, PowerPoint, DOCX, pasted text, and other formats Jot already accepts. Preserve original private files and current access rules. Record a hierarchy equivalent to class → material → section → subsection → chunk, using real headings, pages, slides, paragraph order, and lecture timestamps where available. Mark inferred boundaries. Preserve equations, tables, code, and useful formatting when practical. Ordinary text chunks should usually be about 300–700 tokens; keep coherent short sections intact.

Represent separately: stable logical material ID, stable logical section/chunk ID, immutable content revision ID, and SHA-256 content hash. Store source locator, order, extraction method/status, token count, timestamps, optional visual-asset pointer, and enough data to identify the exact revision used by a question. A hash is a change/deduplication signal, never a replacement for a logical ID. Reconcile revisions using structure and content, not slide number alone. Reuse unchanged extraction or embedding results, reprocess changed portions, preserve historical citations, and prevent an old job from publishing over a newer revision.

Add SQLite FTS5 lexical search with BM25 ranking as a usable baseline. Provide authorized internal operations to list materials, search by class/query/filter, fetch a section/chunk, and fetch a referenced slide/page or original visual. Return bounded snippets and stable source IDs in search; fetch full text only when needed. An ordinary topic query must not load all lectures into model context. Search, direct fetch, images, cached results, graph sources, and AI context construction must apply the same current membership, ownership, visibility, publication, schedule, and answer-key rules. Invalidate or filter stale search results after edits, deletion, release changes, or access revocation.

Use an existing embedding provider only if available; otherwise implement an optional versioned embedding interface and keep the FTS5 path fully functional. Embeddings may help discovery and matching, never establish prerequisites, difficulty, or mastery. Generated visual descriptions must be labeled as generated and kept distinct from source quotations.

## 2. Class knowledge graph

Add class-scoped, stable concept identities with canonical name, assessable description, aliases and language tags, optional parent topic, validation state, provenance, and timestamps. Keep source hierarchy distinct from conceptual relationships. A concept should be independently assessable; merge obvious synonyms without collapsing different learning objectives. Support deprecation and explicit merge mappings while retaining auditable historical evidence. Do not silently move mastery between concepts whose meaning changed.

Support typed edges: part_of, prerequisite_for, related_to, and applied_in. A prerequisite edge records essential/helpful necessity, explicit/inferred provenance, proposed/validated/rejected state, explanation, and exact authorized source references. Explicit means an identifiable source says so; it does not guarantee educational validity. Teaching order and similarity are weak candidate signals, not proof of prerequisites. Only validated prerequisites drive recommendations. An essential prerequisite is not a ban on studying a downstream concept.

On indexing, extract candidate assessable concepts, retrieve duplicate candidates, normalize names and aliases, map chunks to concepts, and propose typed relationships. Use structured, locally validated provider output; require referenced IDs to exist in the same class and support the stated claim. Model confidence numbers are not calibrated probabilities. Keep proposals separate from validated relationships.

Reject missing or cross-class nodes, unsupported edge types, duplicate edges, self-prerequisites, bad references, and cycles in the prerequisite_for subgraph. Other edge types may cycle. Perform prerequisite cycle checks and insertion in one SQLite transaction, including concurrent writes. Flag detectable contradictory directions for review. Provide a functional manager interface to inspect sources, rename/merge concepts, approve/reject proposals, and add/remove edges. Reuse existing class-manager or capability checks; do not invent a professor role that bypasses current permissions.

## 3. Secure, source-grounded question infrastructure

Extend immutable generated quiz/exam content and the current run/attempt path rather than building a second assessment engine. Add a reusable class-scoped question bank, with stable item/family IDs and mappings to primary/secondary concepts, difficulty, type, language, source chunk plus immutable revision, generation model/version, validation state, rubric, explanation, and answer specification. Personal assessments must keep their existing independent ownership and immutable question snapshots; a former class member must not gain access to the class bank through a personal assessment. Retain existing optional generation instructions as lower-trust preferences and reject unsupported source claims. Preserve standard quizzes, practice exams, and Reasoning Mode.

Use four cognitive-demand levels: 1 recognition/recall; 2 conceptual explanation; 3 application or multistep reasoning; 4 analysis, synthesis, or unfamiliar transfer. Difficulty is not prompt length or obscure wording. Validate source support, concept alignment, correct answer, distractors, ambiguity, difficulty, duplicate variants, language, leakage, and rubric completeness. Never deliver an unvalidated or incomplete item as a graded question. Seed modest pools for important concepts, reuse eligible items, replenish in background, and provide a validated generation fallback or an explicit temporary-unavailable state when a pool is empty. An exam needs a curriculum coverage plan and allocated concepts before source retrieval; a top-ranked-chunks query alone is insufficient.

Define separate server-private and student-public schemas for every existing question delivery path, including material detail, run creation, prefetch, review, caches, and errors. Audit existing Live WebSocket events for answer leakage; do not add assessment delivery to that channel unless the current contract calls for it. Before a feedback policy authorizes release, student payloads may include only question/attempt identifiers or an opaque submission token, prompt, opaque per-attempt option IDs and display text, intended visible level/concept labels, and interaction metadata. They must not expose correct choices, is_correct flags, hidden mappings, rubrics, model solutions, misconceptions, or private answer-key citations. Persist randomized option mappings server-side. Grade on the server from an immutable question snapshot; ignore client claims of correctness, score, or XP. A submitted attempt does not by itself release a reusable exam key. Enforce each assessment's feedback-release policy on explanations, solutions, citations, and review tutors.

Track item families, near duplicates, exposures, and prior use when choosing a question. Repeating a memorized variant must not count as independent evidence.

## 4. Assessment behavior

Allow standard quizzes to target concepts, selected uploads, or full-class scope with configurable count, mixed difficulty, existing optional instructions, multilingual output, and optional existing Reasoning Mode. Keep current standard quiz/exam workflows functional. Add Mastery Ladder as another assessment mode, not a replacement.

For each selected concept, start at Level 1 and progress through Levels 2–4. The assessment declares its grading policy before the first answer:

- **Objective-only:** Server-graded correctness controls progression.
- **Reasoning-required:** Correctness and validated rubric-based reasoning quality both control progression. Reuse the existing reasoning submission, snapshots, retries, and provider infrastructure, but do not confuse its current sufficiency-to-submit decision with a judgment that reasoning is sound. Add a distinct structured rubric evaluation where progression requires it.

A failed graded response offers one recovery item from a different question family at the same level by default. Passing recovery advances to the next level and records both observations. Failing recovery ends only that concept's ladder. If no independent recovery item is available, pause with an unavailable state; do not record another failure. A skip ends current concept progression without creating incorrectness evidence. Configure the recovery count/policy server-side. A previously strong student's unexpected low-level failure follows the same distinct verification path; preserve the failure, do not auto-pass, and do not erase established mastery from one miss. Multi-concept ladders keep separate progression and terminal states.

Prefetch only safe public question projections. Keep answer keys and option mappings on the server. A reasoning evaluation error leaves the submitted response intact in pending/failed-grading state, creates no negative correctness or mastery evidence, and can be retried or resumed without duplicate scoring. Do not hold a database transaction during a provider call. Use operation IDs, response digests, conditional state transitions, and uniqueness constraints so repeated submissions and late provider results cannot apply twice or overwrite a newer state.

## 5. XP, accuracy, and mastery

Use one scoring service for standard quizzes, exams, and ladders. Keep three distinct measures: XP for participation, objective accuracy for performance, and mastery for estimated current concept proficiency. Store reasoning quality separately; if an assessment includes it in an official grade, show the declared weight.

Start with configurable XP awards of +5 for a valid response, +5 for a correct answer, +5 for accepted meaningful reasoning, +10 for assessment completion, +20 for a completed four-level ladder, and +15 for verified improvement. Award only after the relevant server event is valid. Use a unique event key tied to user, attempt/response, and award type. Cap repeat-family and per-session awards, reduce or eliminate repeat rewards, and reject empty reasoning. A replayed request must return the original outcome without minting XP again. Accuracy distinguishes correct, incorrect, skipped, unanswered, pending grading, and invalid grading; provider failures never become wrong answers.

Store append-only, owner-bound valid evidence observations with concept and question/family IDs, immutable attempt/response reference, difficulty, correctness in [0,1], reasoning result, grading policy, quality/independence weight, timestamp, and algorithm version. The ledger is authoritative; current mastery and dated history are rebuildable projections. Shared concept nodes never contain private student mastery. Legacy unattributed attempts cannot enter the ledger.

Implement a deterministic Beta-Binomial-inspired projection per user, concept, and difficulty. For prior Beta(alpha, beta), a valid observation with effective weight w and correctness c updates alpha by w × c and beta by w × (1 − c). Treat fractional weights as heuristic pseudo-counts. Make priors, proficiency threshold, confirmation probability, recency rule, family/session caps, and higher-level transfer discounts versioned configuration. Compute posterior mean, uncertainty, and probability of exceeding the threshold with deterministic numerical code. A candidate confirmation rule is P(proficiency ≥ 0.80 | evidence) ≥ 0.90; tune it rather than treating it as an educational constant.

Expose unassessed, latest demonstrated level, provisional/confirmed current estimate, evidence sufficiency, historical peak, recent growth, last assessment, and retention-review status. Advanced answers may contribute discounted foundation evidence only when the item explicitly assesses that foundation; graph edges alone never propagate mastery. Cap evidence from one family/session and lower weight for ambiguous items, repeats, short-interval attempts, and unreliable grading. Do not use XP or lifetime accuracy as mastery.

Use a documented recency policy that can recognize a learner improving over months. For example, decay old evidence relative to the learner's latest valid observation rather than wall-clock time, then mark stale concepts for review separately. Passage of time alone must not demote a level; one miss must not erase established mastery, while repeated independent recent failures can lower current estimates. Historical peak and event history remain visible for growth. A reasoning-required response contributes to confirmed mastery only after validated reasoning grading, through an explicit versioned mapping; otherwise keep reasoning quality separate.

Provide a replay command/service that rebuilds projections and snapshots from immutable evidence. Before showing confirmed labels, run deterministic synthetic trajectories for: beginner-to-proficient growth, lucky guessing, easy-question farming, consistent proficiency, one-off failure, sustained regression, repeated variants, and grading outage. Assert the intended behavior, document selected defaults and observed simulation results, and label the first-release outputs as estimates rather than empirically validated measurements. Synthetic tests are not empirical calibration.

## 6. Recommendations, dashboard, and calibration

After an assessment, generate explainable practice suggestions from current evidence, confidence, recent errors, validated prerequisite edges, available authorized materials, staleness, and the student's chosen goal. A downstream mistake alone does not prove a prerequisite gap; request diagnostic evidence where needed. Do not interrupt an active assessment with remediation. Record recommendation target/resource, type, explanation, supporting evidence IDs, creation time, and completion/dismissal state. A retention review may be due because evidence is stale; it does not automatically revoke mastery. Every recommended resource must pass current access checks when displayed or opened.

Add a private student dashboard with total XP, recent accuracy, concept proficiency and evidence status, historical snapshots over weeks/months, recent improvement, suggested practice, and due reviews. Concept detail shows description, recent authorized evidence, related concepts and prerequisites, released source materials, and next practice. Handle loading, empty, denied, pending-grading, and unavailable states. Integrate with current styling and quiz/exam screens. Give authorized class managers a simple source-backed graph review/edit screen. Do not expose another student's responses, reasoning, XP, mastery, or recommendations.

Record exposure-aware question telemetry: item/family, intended concept/level, exposure count, response and reasoning outcomes, estimated ability at attempt time, repeated exposure, source/generation version, and review flags. Raw pass rate alone is biased because stronger students reach later ladder stages. Use telemetry initially to flag suspicious items for review, not to auto-relabel difficulty from small samples. Record whether prerequisite recommendations were shown, engaged with, completed, and followed by later target performance, with timing/exposure. Asymmetric performance patterns may flag graph edges. Observational association is not a causal intervention effect; do not claim otherwise or launch intrusive experiments.
